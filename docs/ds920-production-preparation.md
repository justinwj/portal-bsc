## Workstation build and offline image transfer proposal

Use White-Raptor or X1-Pro-Ai with Linux Docker, enough free disk space, and a clean checkout of the independently reviewed source commit. A successful GitHub push is not a deployment. DS920+ is [x86_64](https://kb.synology.com/en-ca/DSM/tutorial/What_kind_of_CPU_does_my_NAS_have); build `linux/amd64` using the existing multi-stage Dockerfile, Node 22 and the repository lockfile. No registry publication is needed.

The following is a **future operator procedure, not executed by Session 7H-A**. In a separate clean checkout, first run `npm ci`, typecheck, tests and build. Select the full reviewed SHA and require `git status --porcelain` to be empty. Keep secrets and owner documents outside the build context.

```powershell
$releaseSha = git rev-parse HEAD
$releaseTag = "portal-bsc:r1-$releaseSha"
docker build --pull --platform linux/amd64 --target runtime --label "org.opencontainers.image.revision=$releaseSha" --tag $releaseTag .
if ($LASTEXITCODE -ne 0) { throw 'Image build failed' }
$releaseImageId = docker image inspect --format '{{.Id}}' $releaseTag
if ($LASTEXITCODE -ne 0) { throw 'Image inspection failed' }
docker image inspect --format '{{.Os}}/{{.Architecture}}' $releaseTag
docker run --rm --entrypoint node $releaseTag --version
$releaseOutputDirectory = (Resolve-Path -LiteralPath '<existing private release output directory outside the checkout>').Path
$releaseArchive = Join-Path $releaseOutputDirectory "portal-bsc-r1-$releaseSha.tar"
docker save --output $releaseArchive $releaseTag
if ($LASTEXITCODE -ne 0) { throw 'Image export failed' }
Get-FileHash -LiteralPath $releaseArchive -Algorithm SHA256
```

Record the source SHA, full image content ID, platform, actual Node patch version, archive byte count and SHA-256 in a private release manifest. The full-SHA tag identifies the build, while the full content ID identifies the immutable image. Rebuilding floating base images can produce a different content ID: retain the tested archive and manifest rather than assuming a later rebuild is identical. Do not export any test data volumes or private documents.

After separate transfer approval, transfer only the image archive, manifest and reviewed configuration via an authenticated private LAN channel (operator-controlled SFTP/SCP or a protected DSM share). Verify the archive checksum **on the DS920+** before Container Manager import / `docker load`. Verify the loaded image's complete ID, platform, revision label and Node version against the manifest. Set `PORTAL_APP_IMAGE` to that verified `sha256:<complete image ID>`, not a floating tag. Confirm the installed Compose accepts this reference with `pull_policy: never`. Never build on the NAS or pull/publish this application through a public registry. Retain the previous image archive separately for rollback.

## Nginx and HTTPS proposal

[nginx.http-proposal.conf](../deploy/ds920/nginx.http-proposal.conf) is the reconciled **complete HTTP routing candidate**. It preserves container port **80**, host binding **8088:80**, `worker_processes auto`, `worker_connections 1024`, and all existing mounts. Replace only the placeholder handler with proxying to `app:3000`, after separate approval and app readiness. The existing bind is `/volume1/docker/portal/nginx/nginx.conf:/etc/nginx/nginx.conf:ro`; logs remain `/volume1/docker/portal/logs:/var/log/nginx`. No certificate mount, new Nginx container or port change is required for this routing preparation.

**HTTPS remains outstanding.** Justin confirmed DSM's Reverse Proxy list is empty and prefers evaluating **DSM HTTPS termination → protected existing HTTP backend on 8088 → Nginx → app**. No rule, hostname, HTTPS source/destination, Portal certificate assignment or trusted source address is configured. Follow the [preferred-option evaluation](ds920-existing-configuration-review.md#preferred-dsm-termination-evaluation--proposed-not-implemented) before selecting an executable trust configuration. The earlier [TLS-only candidate](../deploy/ds920/nginx.conf) remains an unselected fallback. Evaluate backend restrictions, observe actual peer/header behavior, and approve certificate management; do not infer trusted addresses or create anything during preparation. Any loopback rebind requiring Nginx recreation needs separate maintenance approval.

Both candidates overwrite `X-Forwarded-Proto` with the actual scheme and `X-Forwarded-For` with the immediate peer. The HTTP candidate therefore forwards **http**, even if a client claims HTTPS. It routes health/login HTML but **does not provide production authenticated access**: Secure session cookies remain enabled and are not issued over plain HTTP. Never weaken cookies or force `X-Forwarded-Proto: https` to work around this. If DSM is later placed in front, its addresses, overwritten protocol/client-IP headers and backend restrictions require explicit configuration and HTTP security tests. The **100 requests / 15 minutes** limiter could aggregate users behind DSM until trusted client-IP forwarding is verified.

The candidate uses a small upstream keepalive pool and Docker DNS refresh for `app:3000`, streams request/response bodies without proxy disk buffering, disables retries of writes, permits up to **1,000,000,000 decimal bytes**, and allows the application's existing 60-minute upload deadline. [Nginx documents streaming and retry semantics](https://nginx.org/en/docs/http/ngx_http_proxy_module.html). Its size ceiling is an additional limit, not quota enforcement. If an administrator raises the app maximum later, review the Nginx and DSM limits too; never silently raise them beyond the approved antivirus-size policy.

**Compatibility prerequisite:** the upstream `resolve` parameter in open-source Nginx requires **1.27.3 or newer**, as documented by [Nginx upstream configuration](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server). Verify the actual existing container using `nginx -v`; its floating `stable-alpine` tag alone does not establish the installed version. If older, stop and obtain review for a compatible proxy/image plan. No upgrade of the NAS Nginx image is authorized or performed here. An earlier no-pool candidate caused Node premature-close errors after successful proxied downloads and triggered existing storage invalidation in disposable tests; do not revert to that candidate to bypass the version requirement.

Every route, asset and download passes through NestJS; there is no `root`, `alias`, archive extraction or direct NAS service. The existing Nginx `/srv/portal-files` mount is unused by the original placeholder and proposed proxy, but **retain it read-only now**: removing a mount requires container recreation and belongs to separately approved maintenance. Keep the app's legacy mount read-only too. Preserve the log bind, ownership, permissions and rotation policy; the candidates write `/var/log/nginx/access.log` and `error.log`, omitting query strings, headers and bodies. Preserve existing loopback dependency ports and expose no new app/database/cache ports publicly. Private remote access remains an independently approved VPN/private-access decision.
